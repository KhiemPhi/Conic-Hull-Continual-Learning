====================================================================================================
METHOD SPECIFICATION AND COMPONENT ATTRIBUTION
5 first-session LoRAs + per-member RanPAC + oPCA conic read-out, fused in matched
geometry and averaged uniformly.   ImageNet-R / CIFAR100 / CUB200P / ImageNet-A,
T=10, PILOT class order (MT19937 seed 1993+s), 3 seeds (CIFAR100: 2, seed 2 pending).
====================================================================================================

1. NOTATION AND SETUP
--------------------------------------------------------------------------------------------
  f0 : X -> R^d          frozen ViT-B/16 augreg_in21k backbone, d = 768. Never updated.
  T tasks, disjoint label sets Y_1..Y_T;  C_t = union_{s<=t} Y_s  are the classes seen by t.
  Class order pi = RandomState(1993 + seed).permutation(C)   [PyCIL/LAMDA-PILOT convention]
  task t = pi[(t-1)*cpt : t*cpt],  cpt = |C| / T.
  Per task a 10% row split: F_t (fit) and V_t (val). Val is used ONLY to select lambda and
  beta; no gradient ever sees it.

2. MEMBERS  -- ALL TRAINED ON TASK 1 ONLY, THEN FROZEN FOREVER
--------------------------------------------------------------------------------------------
  M = 5 LoRA adapters theta_m. For each targeted module W in S_m:
        W  ->  W + (alpha / r_m) * B_m A_m ,   B_m in R^{d x r},  A_m in R^{r x d},  alpha = 4
  Member m induces a normalised feature map
        phi_m(x) = f0(x; theta_m) / || f0(x; theta_m) ||_2   in  S^{d-1}.

        m         S_m (targeted modules)             r_m   trained on
        q32       attn.qkv, attn.proj                 32   all of task 1
        m32       mlp.fc1, mlp.fc2                    32   all of task 1
        a16       all four                            16   all of task 1
        q32b70    attn.qkv, attn.proj                 32   random 70% of task-1 CLASSES
        q64       attn.qkv, attn.proj                 64   all of task 1

  theta_m is fixed for t >= 2. No backpropagation occurs after the first session.

3. RANPAC HEAD  (per member, closed form, accumulated)
--------------------------------------------------------------------------------------------
  One random projection P in R^{d x D}, D = 10000, P_ij ~ N(0,1), SHARED by all members
  (members differ only through phi_m):
        h_m(x) = ReLU( P^T phi_m(x) )   in R^D
  Second-moment statistics accumulate exactly across tasks:
        G_m^{(t)} = sum_{s<=t} sum_{i in F_s} h_m(x_i) h_m(x_i)^T          in R^{D x D}
        C_m^{(t)} = sum_{s<=t} sum_{i in F_s} h_m(x_i) e_{y_i}^T           in R^{D x |C|}
        W_m^{(t)} = ( G_m^{(t)} + lambda I )^{-1} C_m^{(t)},   lambda in {1e2,1e3,1e4} on val
        l_m(x)    = W_m^{(t)T} h_m(x)                                       (logits)

  Row-wise z-score over the SEEN columns, which is what makes members commensurable:
        z(s)_c = ( s_c - mean_{c' in C_t} s_c' ) / ( std_{c' in C_t} s_c' + eps ),  c in C_t
        z(s)_c = -inf otherwise.

4. ORIENTED-PCA CONIC READ-OUT  (per member, per class)
--------------------------------------------------------------------------------------------
  Whitening, from the accumulated within-class scatter in member m's OWN feature space:
        Sigma_m = (1/N) sum_c sum_{i:y_i=c} (phi_m(x_i) - mu_{m,c})(phi_m(x_i) - mu_{m,c})^T
        Sigma~  = Sigma_m + (0.03 * tr(Sigma_m)/d) I           (shrinkage)
        Lambda_m = chol( Sigma~^{-1} )
  For class c, positives X_c and negatives F_c (other classes this task + all past classes'
  stored rays, subsampled to 2000), both whitened and unit-normalised. Oriented scatter:
        M_c = (1/n) X_c^T X_c  -  gamma * (1/|F_c|) F_c^T F_c ,       gamma = 0.5
  V_c = top-k eigenvectors of M_c (k = min(R,d)): directions where c has second-moment energy
  the negatives do not. Rays are k-means centroids INSIDE that subspace, lifted back:
        A_c = normalise( kmeans_{R'}( X_c V_c ) V_c^T ),   R' = min(R, n_c)   <-- THE CLIP
        A~_c = A_c Lambda_m^{-1}                            (stored in feature space)
  Score of query x against class c -- non-negative least squares over the rays:
        w* = argmin_{w >= 0} || q^ - w^T A_c ||_2 ,  q^ = normalise(Lambda_m^T phi_m(x))
        kappa_m(x,c) = cos( q^ , w*^T A_c )   in (-1,1];  1.0 = x lies inside the cone.

5. FUSION AND PREDICTION
--------------------------------------------------------------------------------------------
  Each member is fused against ITS OWN RanPAC, in ITS OWN geometry (this ordering matters --
  pooling the base first costs 2-3x the val overfit):
        S_m(x) = z( l_m(x) ) + beta_m * z( kappa_m(x, .) )
        beta_m = argmax_{b in B} ( val accuracy , val margin )   lexicographic, |B| = 19
  Then a UNIFORM average of the re-z-scored member scores:
        S(x)  = (1/M) sum_m z( S_m(x) )
        y^    = argmax_{c in C_t} S(x)_c
  No task identity is inferred and no member is selected: every member votes on every input.
  Learned member weights were tested and LOST (-0.18 A-Avg, val-test gap 0.86 -> 2.46).

  A_t = accuracy over test rows of C_t after task t;  A-Last = A_T;  A-Avg = (1/T) sum_t A_t.

7. WHY THE CONE CONTRIBUTES WHAT IT DOES -- IT IS MEMBER DIVERSITY, NOT THE RAY BUDGET
====================================================================================================

  FIRST HYPOTHESIS, NOW FALSIFIED. R' = min(R, n_c), so on datasets whose classes have fewer
  than R fit rows the cone degenerates to one ray per training point and loses the AGGREGATION
  that is its mechanism. CUB200P (median 43 rows) and IMAGENETAP (median 18) are both clipped
  at R=64, and CUB200P is exactly where the cone contributes nothing -- so clipping looked
  like the explanation. It is not, for two independent reasons:

    (i)  IMAGENETAP is the MOST clipped dataset (median 18 rows) and gets the cone's LARGEST
         contribution anywhere, +0.89 A-Last. Clipping is plainly not fatal.
    (ii) An explicit R sweep on CUB200P at budgets that are NOT clipped (f8/f16/f32, all well
         under its 43-row median; the run reports clipped_arms = []) still finds nothing:

       CUB200P, seeds [0, 1, 2], unclipped ray budgets (median 43 fit rows/class)
       config                  A-Last   A-Avg    sd   vs ens     val  val-test
       ens_ranpac (no cone)     90.19   93.36  1.03       --      --        --
       FE|f32|cone              90.27   93.40  0.98    +0.04   94.36      0.96
       FE|f8+f32|cone           90.15   93.34  1.05    -0.02   94.41      1.07
       FE|f8|cone               90.15   93.33  1.01    -0.03   94.36      1.03
       FE|f16|cone              90.10   93.32  1.01    -0.04   94.35      1.02
       FE|f8+f16|cone           90.08   93.32  1.02    -0.04   94.40      1.08
       FE|f8+f16+f32|cone       90.08   93.31  1.03    -0.05   94.43      1.12
       FE|f16+f32|cone          90.05   93.31  1.04    -0.05   94.39      1.08

       All seven configs sit within +-0.05 A-Avg of the plain ensemble against a per-config
       sd of ~1.0 (SE ~0.58) -- indistinguishable from zero. Sizing the rays correctly does
       not create diversity that is not there. NOTE: a seed-0-only read of this sweep showed
       every config strictly <= 0 and val picking the single worst config; neither survived
       the other two seeds. The surviving claim is "the cone is a no-op here", not "the cone
       is harmful here", and val-selection costs an ordinary -0.09 A-Avg rather
       than being anti-correlated.

  WHAT ACTUALLY GOVERNS IT is how much the five members disagree. `headroom` = ORACLE minus
  best single member is the ceiling for ANY rule combining them, and the total gain tracks it
  monotonically across all four datasets:

  dataset      member spread  headroom   D_ens  D_cone   TOTAL   (A-Last)
  CUB200P               0.21      2.49   +0.48   -0.03   +0.45
  CIFAR100              0.28      2.60   +0.48   +0.14   +0.62
  IMAGENETR             1.69      5.87   +1.02   +0.80   +1.82
  IMAGENETAP            2.62      8.62   +0.62   +0.89   +1.51

  On CUB200P the five members land within 0.21 of each other -- they converged to nearly the
  same solution, so neither the ensemble nor the cone has anything to recover. Member
  diversity is a property of the DATASET, not of the design, and it predicts where this
  method pays.

  BETA SELECTION ON SMALL VAL SPLITS. CUB200P's stage-0 val carve is ~94 rows and the
  val-test gap runs ~1.0 across every config. Choosing beta on that split costs
  -0.09 A-Avg versus the best config on test -- small, but it means the per-member
  beta search cannot reliably drive beta -> 0 where the cone does not help. Cross-fitting beta
  over the seen data would make that gate automatic instead of manual (section 10).

9. HOW MUCH IS LEFT -- the oracle ceiling (exp55 diversity block)
====================================================================================================

  dataset      best single   ORACLE  headroom      FE  captured  cv share
  CIFAR100           92.88    95.48      2.60   93.40      20%       -2%
  IMAGENETR          80.94    86.81      5.87   82.58      28%       -8%
  CUB200P            89.99    92.48      2.49   90.16       7%      -15%
  IMAGENETAP         62.89    71.51      8.62   64.27      16%       -9%

  headroom = ORACLE - best single = the ceiling for ANY rule combining these members.
  captured = (FE - best single) / headroom.
  cv share = what a per-CLASS member-selection rule realises, cross-fitted within class.
  It is NEGATIVE everywhere: the residual headroom is row-random, not class-structured, so
  no per-class weighting reaches it. Parameter-free per-row weighting was also tested
  (exp57) and gained +0.08 A-Avg against a pre-registered +0.30 bar -- no lift.

10. RECOMMENDED CONFIGURATION PER DATASET (T=10, PILOT order)
====================================================================================================

  Gate rule: use the conic read-out UNLESS it is measured NEGATIVE. A component that
  helps by a small amount on both metrics is still a help; only CUB200P fails this.

  dataset    cone?       R   A-Last    A-Avg  vs GR A-Last  vs GR A-Avg  D_cone A-Avg
  CIFAR100   yes        64    93.40    96.01         +1.43        +1.36         +0.03
  IMAGENETR  yes        64    82.58    87.01         +0.49        +0.81         +0.46
  CUB200P    NO          0    90.19    93.36         +0.28        -0.49         -0.03
  IMAGENETAP yes        64    64.27    72.23         +0.67        +1.99         +0.07
  MEAN                                               +0.72        +0.92

  'NO' means the conic read-out is measured NEGATIVE on that dataset at every ray budget
  tested (CUB200P: seven configs from f8 to f64, all <= 0), so the method reduces to the
  5-member RanPAC ensemble there. This is a measured gate, not a tuned one -- but it is still
  a per-dataset choice and must be declared as such in any published table. Cross-fitting beta
  over the seen data would make the gate AUTOMATIC (beta -> 0 where the cone does not help)
  rather than manual, and is the preferred fix; CUB200P's anti-correlated val split (section 7)
  is direct evidence that the current single 10% carve cannot do this on its own.

  CAVEATS
    - CIFAR100 is 2 seeds (seed 2 lost to an interrupted run); IMAGENETR/CUB200P/IMAGENETAP
      are 3. The CUB200P R sweep is seed 0 only.
    - Per-cell seed sd is in section 6; IMAGENETAP is the noisiest (FE sd 1.25 A-Last) and its
      A-Last margin is NOT significant (0.9 SE). CUB200P's A-Avg deficit is likewise 0.9 SE.
    - GR-LoRA numbers are published point estimates with no reported spread, so every t-value
      here treats their column as fixed and understates the true uncertainty.
    - T=20 and T=50 are not yet measured under the PILOT order.

11. MEMORY AND COMPUTE vs GR-LoRA
====================================================================================================

  All counts are parameter/element counts; MB assumes float32 unless stated. ViT-B/16 (86M,
  frozen) is common to both and excluded. C = 200 classes, T = 10 tasks, d = 768, L = 12
  blocks, M = 5 members, R = 64 rays, D = 10000 RanPAC features.

11.1 ADAPTER PARAMETERS
--------------------------------------------------------------------------------------------
  OURS -- five heterogeneous first-session LoRAs, count is FIXED in T:
      q32      qkv+proj               r=32     1.77 M
      m32      fc1+fc2                r=32     2.95 M
      a16      qkv+proj+fc1+fc2       r=16     2.36 M
      q32b70   qkv+proj               r=32     1.77 M
      q64      qkv+proj               r=64     3.54 M
      TOTAL                                   12.39 M

  GR-LoRA -- k and v only, but DOUBLED (shared {A,B} + task-specific {A_fit,B_fit}) and one
  new set PER TASK, so the count is LINEAR in T:
      per task  = L * 4 pairs * 2 * d * r = 73728r
      x T = 10   = 737280r
      r = 64  ->   47.19 M      r = 32 -> 23.59 M      r = 16 -> 11.80 M
  Their rank is NOT verified from the paper or the config we have; the model signature
  defaults to 64. At r=64 we use ~3.8x fewer adapter parameters, at r=16 we use ~1.1x MORE.
  THIS COMPARISON IS UNRESOLVED UNTIL THEIR CONFIG IS READ.

11.2 PERSISTENT STATE DURING CONTINUAL LEARNING  (what must survive to accept task t+1)
--------------------------------------------------------------------------------------------
  OURS                                        elements        MB
    LoRA adapters                                 12.39 M        50
    RanPAC Gram G_m (5 x D x D, float64)         500.00 M      4000
    RanPAC C_m / solved W_m                       10.00 M        40
    cone rays (5 x R x d x C)                     49.15 M       197
    whiteners (5 x d x d)                          2.95 M        12
    TOTAL                                                      4298 MB

  GR-LoRA                                     elements        MB
    LoRA adapters (r=64, T=10)                    47.19 M       189
    per-task classifier heads                      0.15 M         1
    class prototypes + FULL covariances          118.27 M       473
    TOTAL                                                       662 MB

  WE ARE 6.5x WORSE HERE, and it is one term: the RanPAC Gram G_m is D x D = 1e8
  elements PER MEMBER and must persist to keep accumulating. In float64 that is 4.0 GB.
  Storing G in float32 halves it to 2.0 GB; it is the single largest lever available and has
  not been tested for numerical impact on the ridge solve.

11.3 DEPLOYED FOOTPRINT  (frozen model, no further tasks)
--------------------------------------------------------------------------------------------
    OURS     LoRA 50 + RanPAC W 40 + cones 197 + whiteners 12          =   298 MB
    GR-LoRA  LoRA 189 + heads 1 (covariances are TRAINING-ONLY, discardable)  =   189 MB

  We are 1.6x LARGER deployed, dominated by the cone rays (197 MB = R*d per class per
  member). An earlier note in this project compared our cones against their 473 MB of
  covariances; that was wrong -- their covariances exist only to synthesise features for
  classifier alignment during training and need not ship.
  The RanPAC projection P (31 MB) is regenerable from manual_seed(0) and is not counted.

11.4 INFERENCE COST PER TEST IMAGE  -- MEASURED ON THIS BOX, NOT ESTIMATED
--------------------------------------------------------------------------------------------
    ViT-B/16 fp32 forward, CUDA, bs=64         3.17 ms / image
    cone_score, R=64, 500 NNLS iters,
      single-thread NumPy on CPU              0.037 ms / (query, class, member)
    OURS      5 x backbone                      15.86 ms
              5 x 200 x cone score              37.20 ms   <-- DOMINATES
              RanPAC projection + solve        ~0.02 ms
              TOTAL                             53.06 ms
    GR-LoRA   T x backbone (entropy select)     31.72 ms

  AS IMPLEMENTED WE ARE 1.7x SLOWER AT T=10, not faster. Every earlier claim in this
  project that we are "cheaper at inference" counted only the backbone passes and treated the
  conic read-out as free. It is not: it is 2.3x the cost of the five backbone passes.

  TWO THINGS THAT REDEEM IT, AND ONE THAT DOES NOT
    (a) SCALING. Our cost is CONSTANT in T (it scales with C and M, not with tasks); theirs is
        LINEAR in T because Eq. 8 evaluates every task-specific module. Crossover is at
        T ~ 17: at T=10 they are cheaper, at T=20 we are (53 ms vs 63 ms),
        at T=50 we are far cheaper (53 ms vs 159 ms).
    (b) THE MEASUREMENT IS UNOPTIMISED. cone_score is single-threaded NumPy on CPU while the
        backbone is fp32 on GPU. A batched GPU NNLS, or fewer than 500 iterations, would move
        this a lot. The number above is what the current code does, not a lower bound.
    (c) WHAT DOES NOT HELP: reducing R. Measured 32.7 / 43.8 / 41.6 / 37.2 / 57.2 us at
        R = 8 / 16 / 32 / 64 / 128 -- nearly flat, because the 500 fixed iterations dominate,
        not the ray count. Cutting members would help linearly, but exp57 measured accuracy
        MONOTONE in K with no subset of size < 5 matching K=5.

11.5 TRAINING COST
--------------------------------------------------------------------------------------------
    OURS      5 LoRA trainings, ALL on task 1, mutually independent -> embarrassingly
              parallel. Zero backpropagation for tasks 2..T. Per task thereafter: one feature
              extraction pass per member, a rank-D ridge solve, and the cone builds.
    GR-LoRA   T sequential LoRA trainings (cannot be parallelised -- task t needs the residual
              subspace of tasks 1..t-1), each with LMS doubling the forward cost, plus a
              20-epoch classifier-alignment loop on synthesised features after every task.

    Wall-clock from this project's own runs (IMAGENETR T=10, 3 seeds, one box):
      our member training  ~3300 s      our read-out (RanPAC + cones + fusion)  ~5900 s
    GR-LoRA has not been run here, so no head-to-head training number exists.

11.6 SUMMARY -- WHERE WE ACTUALLY WIN AND LOSE
--------------------------------------------------------------------------------------------
    WIN   adapter parameters IF their rank is 64      (12.4 M vs 47.2 M)
    WIN   training structure: parallel, first-session only, no backprop after task 1
    WIN   inference scaling: constant in T vs linear in T (crossover T ~ 17)
    LOSE  persistent memory during CL          (4.3 GB vs 0.66 GB) -- the RanPAC Gram
    LOSE  deployed footprint                   (298 MB vs 189 MB) -- the cone rays
    LOSE  inference wall-clock at T=10         (53 ms vs 32 ms) -- the NNLS

11.7 UNVERIFIED -- DO NOT PUBLISH THESE WITHOUT CLOSING THEM
--------------------------------------------------------------------------------------------
    - GR-LoRA's LoRA rank. Everything in 11.1/11.2/11.3 for their column assumes r=64 from the
      model signature. At r=16 the adapter comparison REVERSES.
    - Whether their reported wall-clock reflects the T-pass entropy selection in interface().
